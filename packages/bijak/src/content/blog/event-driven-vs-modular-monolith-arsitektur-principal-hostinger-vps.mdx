Kegagalan infrastruktur akibat *cascading latency* dan tagihan *managed cloud service* yang membengkak hingga puluhan juta rupiah setiap bulan adalah mimpi buruk yang kerap menimpa tim rekayasa perangkat lunak skala menengah hingga *enterprise*. Banyak Principal Architect terjebak dalam arus tren migrasi *microservices* berorientasi *Event-Driven Architecture* (EDA) tanpa memperhitungkan kompleksitas operasional, latensi riil *network hop*, dan fenomena *eventual consistency* yang berisiko mengacaukan konsistensi data finansial. Di sisi lain, membiarkan aplikasi berkembang sebagai monolith tradisional yang tidak terstruktur hanya akan melahirkan *spaghetti code* yang sulit di-maintain.

Dalam merancang arsitektur sistem modern, pilihan terbaik tidak selalu berada di ujung spektrum yang paling kompleks. *Modular Monolith* hadir sebagai alternatif rasional yang menawarkan batas domain terisolasi (*encapsulated boundaries*) dengan latensi panggilan fungsi (*in-process method calls*) secepat mikrodetik, tanpa overhead jaringan. Sebelum memutuskan untuk memecah sistem menjadi ratusan produsen dan konsumen pesan (*publish-subscribe*), pertimbangkan dampak arsitektur terhadap pemanfaatan sumber daya server serta strategi [Optimasi Latensi Sistem Skala Enterprise](/blog/pgvector-optimasi-skala-ai-produksi-hostinger-kvm-vps/) yang presisi.

### Dilema Fundamental: Konsistensi Data dan Latensi Pesan

Perbedaan paling mendasar antara Event-Driven Architecture dan Modular Monolith terletak pada eksekusi transaksi dan model konsistensi data. Pada Modular Monolith, transaksi bisnis umumnya bersifat *ACID* (*Atomicity, Consistency, Isolation, Durability*) dengan *strong consistency*. Ketika pengguna melakukan transaksi, database utama akan mengunci baris data (*row locking*) atau menggunakan kontrol konkurensi optimistis untuk memastikan data langsung valid seketika.

Sebaliknya, Event-Driven Architecture mengadopsi model *BASE* (*Basically Available, Soft state, Eventual consistency*). Ketika sebuah *event* diterbitkan oleh service A, service B mungkin baru memprosesnya beberapa ratus milidetik kemudian. Jika terjadi lonjakan *throughput* konkurensi, antrean broker seperti Kafka atau RabbitMQ dapat mengalami *consumer lag*. Hal ini berisiko memunculkan data yang tidak sinkron sementara waktu (*race conditions*).

| Parameter Evaluasi | Event Broker (Kafka / RabbitMQ) | In-Memory Event Bus (Modular Monolith) |
| :--- | :--- | :--- |
| **Mekanisme Komunikasi** | Jaringan (TCP/IP Protocol, Asynchronous) | Memori Lokal (In-Process Sync/Async Calls) |
| **Latensi Pesan** | Sub-milidetik hingga Ratusan Milidetik | Nanodetik hingga Mikrodetik |
| **Konsistensi Data** | *Eventual Consistency* (Membutuhkan Saga Pattern) | *Strong Consistency* (Database Transactional Boundary) |
| **Kompleksitas Operasional**| Tinggi (Zookeeper/KRaft, Cluster Management, Rebalancing) | Sangat Rendah (Single Deployment Unit) |
| **Ketahanan Pesan (*Persistence*)**| Tinggi (Disimpan di Disk dengan *Replication Factor*) | Terbatas (Memori Hilang Jika Instance Restart) |

### Analisis Trade-off Arsitektur Sistem

Memilih antara EDA dan Modular Monolith bukanlah sekadar membandingkan mana arsitektur yang lebih modern, melainkan mengevaluasi *trade-off* teknis yang sesuai dengan kapasitas operasional tim serta target performa bisnis.

| Dimensi Arsitektur | Event-Driven Architecture (EDA) | Modular Monolith |
| :--- | :--- | :--- |
| **Skalabilitas Konkurensi** | Sangat Tinggi (Skala Horizontal Independen per Consumer) | Tinggi (Skala Vertical/Horizontal pada Seluruh Monolith) |
| **Latensi End-to-End** | Bervariasi (Tergantung Network Overhead & Broker Queue) | Sangat Rendah & Prediktif (*In-Memory Execution*) |
| **Konsistensi Data** | Kompleks (Perlu Penanganan *Idempotency* & *Dead Letter Queue*) | Sederhana (Transaksi Database Tunggal / *Atomic*) |
| **Biaya Infrastruktur** | Tinggi (Butuh Banyak Instance Server & Managed Broker) | Sangat Efisien (Pemanfaatan CPU/RAM Maksimal pada VPS) |
| **Kompleksitas Debugging** | Sangat Tinggi (Membutuhkan *Distributed Tracing*) | Rendah (Cukup *Centralized Logging* dan *Stack Trace*) |

Untuk sistem yang belum membutuhkan *throughput* jutaan *event* per detik, Modular Monolith dengan *in-memory event bus* (seperti MediatR pada .NET atau ApplicationEvents pada Spring) merupakan pilihan paling efisien. Anda tetap mendapatkan pemisahan logika domain yang bersih (*clean architecture*) tanpa harus membayar biaya operasional infrastruktur broker yang mahal.

### Optimasi Cloud Infrastructure dan Efisiensi TCO

Salah satu kesalahan terbesar Principal Architect adalah menerapkan Event-Driven Architecture berukuran besar di atas infrastruktur *managed cloud* yang mahal tanpa menghitung rasio *cost-to-performance*. Menjalankan kluster Kafka multi-node, ditambah puluhan *microservices* di *managed Kubernetes*, dapat dengan cepat menyedot anggaran TI perusahaan.

Dengan beralih ke arsitektur Modular Monolith atau EDA berskala moderat yang di-host mandiri (*self-hosted*), Anda dapat merealisasikan [Efisiensi Biaya Infrastruktur Cloud dengan Self-Hosting](/blog/pgvector-self-host-efisiensi-coolify-hostinger-vps-vs-managed-cloud/) hingga 70%. Pemanfaatan server bare-metal atau Virtual Private Server berkinerja tinggi memberikan kontrol penuh atas alokasi CPU, RAM, dan kecepatan disk I/O.

### Panduan Strategis Principal Architect

1. **Mulai dari Modular Monolith**: Jangan terburu-buru mengadopsi EDA jika tim operasional Anda belum siap menangani *distributed tracing* dan *eventual consistency*. Susun aplikasi dengan batas modul yang jelas (*strict module boundaries*).
2. **Gunakan In-Memory Event Bus Pertama Kali**: Manfaatkan event internal aplikasi untuk mengisolasi logika domain. Jika suatu saat modul tertentu membutuhkan skala independen, modul tersebut dapat dipisah menjadi *microservice* terpisah dengan mudah.
3. **Ekstraksi ke EDA Saat Terjadi Bottleneck Riil**: Terapkan Kafka atau RabbitMQ hanya ketika terdapat kebutuhan integrasi sistem pihak ketiga, pemrosesan latar belakang yang berat (*heavy background jobs*), atau kebutuhan skalabilitas horizontal pada modul spesifik.
4. **Optimalkan Platform Hosting**: Jalankan infrastruktur Anda di atas VPS berkinerja tinggi seperti Hostinger KVM VPS untuk menekan biaya bulanan tanpa mengorbankan kecepatan eksekusi data.
