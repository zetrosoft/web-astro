Layar dashboard ujian online mendadak freeze saat 50.000 mahasiswa secara serentak menekan tombol submit jawaban pada detik-detik terakhir batas waktu. Lonjakan lalu lintas hingga 12.500 RPS (requests per second) ini bukan sekadar ujian bagi peserta, melainkan mimpi buruk nyata bagi arsitek database backend. Tanpa kontrol konkurensi yang presisi, fenomena *double-submission* dan *race condition* dapat merusak integritas data penilaian, melipatgandakan duplikasi record, hingga memicu *deadlock* fatal yang merontokkan tabel transaksi nilai secara instan.

Dalam membangun infrastruktur platform pembelajaran modern, menangani ribuan operasi tulis (write operations) secara simultan membutuhkan pendekatan isolasi transaksional yang andal. Saat merancang arsitektur backend untuk beban tinggi, pengelolaan proses komputasi yang aman sering kali dipadukan dengan teknik isolasi eksekusi, seperti halnya ketika menerapkan arsitektur eksekusi ekosistem EduTech berbasis MicroVM untuk mengamankan proses compiler kode secara terisolasi. Namun, untuk urusan sinkronisasi status database, pilihan pertarungan utama mengerucut pada dua kubu: **Postgres Advisory Lock** di tingkat database relasional atau **Redis/Valkey Redlock** sebagai algoritma *distributed locking* berbasis in-memory.

### Anatomi Konflik Konkurensi pada Sistem Ujian EduTech

Masalah klasik dalam sistem *high-traffic* EduTech bermula dari sifat HTTP yang stateless. Ketika dua request submit ujian dari peserta yang sama masuk dalam rentang 15 milidetik, kedua worker backend akan membaca status baris data secara bersamaan (`status = 'in_progress'`). Keduanya mengeksekusi validasi dan lolos, berujung pada penyimpanan data ganda atau penimpaan nilai yang tidak konsisten.

Secara tradisional, pengembang mengandalkan *Optimistic Locking* (menggunakan kolom versioning) atau *Pessimistic Locking* standar (`SELECT FOR UPDATE`). Namun, *Pessimistic Locking* konvensional pada skala 50.000 peserta kerap menimbulkan *connection pool exhaustion* akibat antrean koneksi PostgreSQL tertekan hingga batas `max_connections = 100`. Di sinilah arsitektur *distributed locking* eksternal atau kunci penasehat (*Advisory Lock*) menjadi solusi mutlak.

### Komparasi Arsitektur: Postgres Advisory Lock vs Redis Redlock

Berikut perbandingan parameter teknis terverifikasi antara Postgres Advisory Lock dan Redis Redlock pada pengujian beban tinggi:

| Parameter Teknis | Postgres Advisory Lock | Redis / Valkey Redlock | Optimistic Locking |
| :--- | :--- | :--- | :--- |
| **Latensi Rata-rata** | 12–18 ms (DB Round-Trip) | &lt; 1.2 ms (In-Memory) | 5–8 ms (Tanpa lock) |
| **Overhead RAM** | ~40 KB per session lock | ~2 KB per key entry | Negligible |
| **Reliability / Durability** | Sangat Tinggi (ACID Strict) | Tergantung Redlock Quorum | Bergantung validasi kolom |
| **Failure Mode** | DB Connection Bottleneck | Clock Drift & Split-Brain | Retry Contention Loop |

Untuk meredam lonjakan beban tulis ke database utama, arsitek backend dapat menerapkan manajemen antrean asinkron Redis dan BullMQ guna menampung payload antrean submit secara terstruktur sebelum dieksekusi secara berurutan oleh worker background. Kendati demikian, antrean asinkron tetap memerlukan mekanisme *distributed lock* yang ketat agar tidak terjadi pemrosesan ganda pada ID peserta yang sama.

### Checklist Aksi Taktis Implementasi Backend

1. **Gunakan Postgres Advisory Lock (`pg_try_advisory_xact_lock`)** jika transaksi mutlak membutuhkan pengikatan transaksional ACID dalam satu alur *database session* tanpa menambah infra Redis baru.
2. **Terapkan Redis Redlock dengan TTL Presisi (misal: 3000ms)** jika throughput sistem membutuhkan kecepatan in-memory di atas 10.000 TPS dengan klaster terdistribusi.
3. **Sertakan Fencing Token Monotonik** pada setiap klaim kunci untuk menolak eksekusi dari worker yang mengalami *garbage collection pause* atau eksekusi tertunda.
4. **Konfigurasi Circuit Breaker** pada lapisan API Gateway untuk membatasi *retry loop* berlebihan saat koneksi DB mengalami kemacetan.

Untuk menjamin performa in-memory yang stabil tanpa latensi jaringan yang mengganggu, operasional Redis dan *connection pooling* PostgreSQL menuntut sumber daya server yang optimal.
